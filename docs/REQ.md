# 多智能体 SRS 智能编制系统 — 需求规格（精简版，v3）

## 1. 范围与总体目标

面向自动化编制软件需求规格说明书（SRS）的多智能体系统。通过解析—挖掘—澄清—成文的闭环流程，多轮迭代收敛需求质量，输出符合规范的 SRS 文档；支持“消融模式”以评估各环节对结果与效率的影响。

### 1.1 技术架构

项目使用 **LangGraph** 构建工作流，包含以下4个节点：
- **ReqParse**：需求解析节点
- **ReqExplore**：需求挖掘节点
- **ReqClarify**：需求澄清节点
- **DocGenerate**：文档生成节点

### 1.2 文档生成目标

整个项目只为生成以下版本的SRS文档：

1. **srs_document_no-explore-clarify**：在 `parse` 节点完成后生成
2. **srs_document_no-clarify**：在第一次 `explore` 节点完成后生成
3. **srs_document_iter{N}**：在每次 `clarify` 节点完成后生成（最后一次iter版本即为最终主流程版本）

## 2. 功能性需求（FR）

### 2.1 角色层（智能体）能力

* **FR-001 需求解析智能体（ReqParse）**
  系统应将自然语言需求解析为**去重的原子需求**列表，仅保留可执行、可验证的独立句，剔除疑问句与主观表述。
* **FR-002 需求挖掘智能体（ReqExplore）**
  系统应在解析基础上补充缺口（异常路径、权限、数据完整性等），形成**业务语言**表述的全局需求清单，采用 `[{id:"REQ-001", text:"…"}]` 且 ID 连续递增。
* **FR-003 需求澄清智能体（ReqClarify）**
  系统应加载**基准 SRS**，对清单逐条给出一致性评分，评分集固定为 **{+2,+1,0,-1,-2}**，并提供**不超过 60 字**的评分理由；得分为负的条目在本轮应被移除，其中 **-2** 的条目列入**禁用清单**禁止复用。
* **FR-004 文档生成智能体（DocGenerate）**
  系统应将最终清单生成 SRS 文档（Markdown），覆盖规定章节；生成时只依赖清单内容，不引入外部知识或实现细节。

### 2.2 任务层（工作流与控制）

* **FR-005 工作流编排**
  系统应使用 **LangGraph** 实现“**需求输入与解析 → 需求挖掘与修正 → 需求澄清 → SRS 生成**”的闭环流程。工作流包含4个节点：ReqParse、ReqExplore、ReqClarify、DocGenerate。
* **FR-006 迭代优化**
  系统应支持多轮迭代；每轮在澄清反馈后对清单进行修正扩充，直至达到设定轮次或收敛标准。
* **FR-007 基准对照输入**
  系统应支持导入**基准 SRS 文本**，用于澄清阶段评分与迭代指导。

### 2.3 消融实验（Ablation）

* **FR-009 消融模式参数**
  系统应支持运行参数 `ablation_mode`，取值：`default`（或空）、`no-clarify`、`no-explore-clarify`。
* **FR-010 模式：no-clarify**
  在 `no-clarify` 下，系统应**跳过 ReqClarify**；对当轮生成的每条需求默认赋予 **0 分**并记录到**得分历史**，`global_iteration` 正常递增，后续仍按聚合与成文流程执行。
* **FR-011 模式：no-explore-clarify**
  在 `no-explore-clarify` 下，系统应**同时跳过 ReqExplore 与 ReqClarify**；将原子需求直接映射为 `REQ-xxx` 条目（`score_in_iteration=0`，`iteration=0`）进入聚合与成文。
* **FR-012 消融输出与对比**
  系统应在流程结束输出**对比信息**（至少包括：总需求数、进入最终清单数、被禁用 ID 数、各代理耗时汇总、各需求得分历史轨迹概览），用于对比不同消融模式的影响。

### 2.4 结果与评估

* **FR-008 编制耗时统计**
  系统应统计自需求输入到 SRS 终稿的**总耗时**，用于衡量编制效率。

### 2.5 评分理由隔离（新增）

* **FR-013 评分理由隔离与审计**
  a) **隔离**：`ReqExplore` 在其输入上下文中**只能看到 `id` 与 `score`**，**不得看到 `reason`** 或其任何片段/改写文本。
  b) **保存**：`ReqClarify` 产生的 `reason` 可用于**日志/报告/审计**；若落库到状态/文件，也**不得**被用于构造 `ReqExplore` 的消息。

## 3. 设计约束与依赖（CON）

* **CON-001 评分标度约束**
  澄清阶段的评分必须严格使用 **{+2,+1,0,-1,-2}**；**-2** 的条目进入禁用清单，后续迭代不得复用相同方向或 ID。

## 4. 典型用例（概述）

* **UC-01：从资料到 SRS（默认模式）**
  前置：提供需求资料与基准 SRS。
  主流：解析 → 挖掘 → 澄清（评分与反馈）→ 若干迭代 → SRS 生成。
  成功：输出的 SRS 完整覆盖经澄清后的清单，并记录全过程耗时与得分轨迹。
* **UC-02：带禁用清单的迭代（默认模式）**
  触发：出现与基准 SRS 明确冲突条目。
  主流：评分 **-2** 的条目加入禁用清单；后续不得复用其方向或 ID。
  成功：最终清单不含被禁用方向。
* **UC-03：消融—no-clarify**
  主流：解析 → 挖掘 →（跳过澄清）→ 多轮挖掘 → 聚合 → 成文；所有条目当轮默认 0 分并记录历史。
  成功：输出对比信息显示与默认模式在“需求数、文档完整性、耗时”上的差异。
* **UC-04：消融—no-explore-clarify**
  主流：解析 →（跳过挖掘与澄清）→ 原子需求直接聚合 → 成文。
  成功：输出对比信息显示与默认模式在“时间与质量权衡”上的差异。
